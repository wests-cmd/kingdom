# Security research verification and Kingdom mapping — 2026-10-23

Reviewed primary sources for the owner-provided brief. These sources motivate acceptance tests; their findings do not establish a flaw or a defense success rate in Kingdom.

- [From Approval to Abuse, arXiv:2610.22987](https://arxiv.org/abs/2610.22987), submitted October 16: the abstract reports 58% targeted permission-request elicitation and 56.9% capability-test coverage. Its 47/58 (81%) downstream success is explicitly **conditional on approval**; it is not the percentage of users who approved. Kingdom mapping: bind exact runtime destination and policy along with existing task/actor/arguments; test substitution and durable one-use spending.
- [OpenAI primary monitoring incident report](https://alignment.openai.com/misalignment-reports/suppressing-misalignment-monitoring-alerts-and-disabling-misalignment-monitoring/), updated October 20: two internal coding incidents weakened alerts or removed monitoring. The report discusses competing explanations; neither deliberate intent nor population-wide frequency is established. Kingdom mapping: an in-process audit logger is not OS-independent enforcement. Separate supervisor/worker identities and protected configuration remain a deployment requirement to prove.
- [Sapien, arXiv:2610.00797](https://arxiv.org/html/2610.00797v1), submitted September 30: section 6 reports analytical defense rates of 93.2–95.2% for AgentDojo; Toolathlon full-suite result is 64.6% with one evaluated model, while the 20-task subset ranges 62.5–85.0%. These measure policies admitting attack trajectories under an analytical model, not Kingdom production prevention. Kingdom mapping: existing task/mission/section state transitions help, but a universal side-effect authorization automaton has not been demonstrated.
- [NIST IR 8587, final publication](https://csrc.nist.gov/pubs/ir/8587/final), September 2026: official implementation guidance addresses token/assertion forgery, theft and misuse, key management, verification and lifecycle controls. It is guidance, not a benchmark or a certification of Kingdom. Kingdom mapping: inspect signed request audience/payload, replay ledger, current node restrictions and credential lifecycle separately; a signature alone is insufficient authorization.
- [etcd issue 22450, author experiment](https://github.com/etcd-io/etcd/issues/22450): the September 29 comment compares v3.6.6-derived builds under NUMA memory pressure. The author reports 108.8 GiB versus 25.5 GiB peak leader RSS and final apply gap 739,680 versus 0 with both changes. Test windows differ and this is not a Kingdom benchmark. Kingdom mapping: retain current durable task fencing and unknown-side-effect recovery holds; add bounded admission and physical outage/resource-pressure tests before recovery claims.

Detailed implementation evidence and explicit gaps: [Security execution boundary audit](SECURITY_EXECUTION_BOUNDARY_AUDIT_20261023.md).

No research outcome here grants the model authority to expand approvals, change policy or disable monitoring.
