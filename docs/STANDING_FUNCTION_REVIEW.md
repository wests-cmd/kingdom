# Standing review for bounded function work

This optional owner-only control removes per-proposal review for one narrow
workflow class. It is **off by default**. It is not a general repository reviewer,
a process grant, an automatic installer or release authorization.

At autonomy level5 the authenticated owner can call
`POST /work-programmes/{id}/standing-review` with the current `expected_revision`
and a `scope`: `enabled`, one relative `write_prefix` beneath `projects/`, exact
`read_sources` path→SHA256 mappings, and `max_missions` (1–12).
The programme must name one explicit local model. The saved consent pins its public
configuration and a scope version. Only the owner control can change this consent;
model text and retrieved knowledge cannot.

The deterministic reviewer requires two local plans, critique and synthesis from
the pinned connection, a validated mission with3–6 steps, one write under the
approved prefix and one final immutable `bounded_batch_size.v1` check. Reads from
other project paths require their exact approved digest. Unknown syntax is data
until the finite AST interpreter accepts it. Commands, native project tests,
desktop/network effects, offload, model-selected tests and unresolved requirements
are outside this scope. Existing worker tool grants are still enforced.

For copy/check outcomes with approved sources, planning can use the compact
`function_copy.v1` blueprint selection (`blueprint`, `source`, `target`). Kingdom
compiles the mechanics, validates the result and applies the same review scope.
This avoids asking a small model to invent the dependency schema. Compilation is
not approval; an unknown blueprint or additional parameters is rejected.

The Kingdom runner reviews at most one retained proposal per cycle. It binds the
same durable mission/backlog and consumes the configured mission budget. Normal
verified receipts, bounded repairs and dependency selection advance the work.
Before further mission dispatch, consent revocation, model changes, source digest
changes or policy downgrade stop advancement. No model or tool receives the owner
API credential or additional capabilities. An owner manual review remains separate.

Section integration still requires its separate reviewed native project-test
suite. This control cannot pass that gate or claim whole-backlog autonomy. Broader
repository work needs an independently reviewed executor/test environment and
appropriate task-bound authorization; do not broaden this scope to simulate it.
