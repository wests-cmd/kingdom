# Shared platform delivery

Built-in Workbench uses persisted `/requests`: session/project scopes,
idempotency, polling, cancellation and reconnecting conversations. Clock,
status and priorities have deterministic routes. Clear action requests use
native tool sessions; other questions use models. Routing is conservative,
not universal language understanding. Model completion never proves code
quality; independently verified tool results remain separate evidence.

Completed answers enter the scoped project vault. Conversation history and
retrieval stay in the same scope. Memory supports Markdown ZIP/JSON interchange,
revision-checked edits, atomic import, index rebuilding, trash and restore.
Credential-shaped filtering cannot discover all arbitrary secrets. Imported
notes remain untrusted and grant no permissions.

Durable schedules enqueue requests and optionally run bounded jobs at levels
4–5 when explicitly enabled. Defaults are paused with autorun off. One
unfinished request per schedule prevents an unseen queue. Jobs needing review
are held. App lifecycle owns polling; service startup survives host reboot.
These guarantees do not imply exactly-once external effects.

Optional browser voice starts only on a click and requires transcript review
before sending. Stop/discard and text fallback remain available. Recognition
may use the browser vendor; offline Whisper/Kokoro is not installed or claimed.

Two independent installed Kingdoms passed mutual pairing, signed heartbeats,
peer restart continuity and a real remote analysis lease with controller
verification. An owner SSH relay carried unchanged signed messages. Direct
automatic networking is not proven. Guarded migration preserved the signing
key and rejected active work or existing remote pairings.

Governance offers encrypted, write-only optional Stripe configuration.
Payment intents have durable identity, exact policy authorization, owner
currency/amount limits and provider idempotency. Uncertain outcomes require
reconciliation. Tests used isolated HTTP fixtures; no live account or funds
were used. Receiving payments and buying from merchants are different
integrations: universal shopping, checkout adapters and OAuth account linking
are not implemented by the Stripe receiving adapter. Live operation requires
the owner's provider connection and any merchant-required authentication.

172 targeted backend tests,16 frontend tests and production build passed.
Installed two-host evidence remains in private owner outputs, not in public
source with addresses or credentials. Existing external connectors must adopt
the shared request contract; they are not automatically migrated. Desktop and
phone browsers can use the same responsive workspace when the private server
is reachable. No new public exposure or automatic account sign-in is claimed.
