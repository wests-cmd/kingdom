# Decision-model research — 25 October 2026

## Decision

Use two small, bounded learned selectors on DT1 first: one ranks installed models; the other ranks eligible worker placements for an existing plan. They are selectors, not planners or permission engines. Nimble is a useful training/data-design reference, but its published neural model is not a credible fit for this DT1. No installations, downloads of model weights, training, or hardware benchmarks were performed for this research.

## Nimble: pinned source and feasibility

Reviewed upstream commit [4edb0703a2e75d0170c3a45645a1961f4d1a2867](https://github.com/bespokelabsai/nimble/tree/4edb0703a2e75d0170c3a45645a1961f4d1a2867). It selects caller-supplied enum/Boolean candidates from logits rather than generating a plan. The README documents Apple Silicon MLX and NVIDIA BF16 execution; 9B BF16 weights alone require about 18 GB, before working memory. MLX's documented runner does not support quantized weights. Consequently the documented runtime exceeds DT1's approximately 3.7 GiB RAM, and its GPU paths do not apply to the Core 2 Duo without AVX. These are compatibility conclusions, not measurements on DT1. [Pinned README](https://github.com/bespokelabsai/nimble/blob/4edb0703a2e75d0170c3a45645a1961f4d1a2867/README.md)

The supplied trainer uses BF16 LoRA on pinned Qwen3.5-9B, with candidate-logit cross entropy. Its outputs include adapters, tokenizer, model/prompt contract, audits, and evaluation metrics. The guide describes NVIDIA training, not a tiny CPU training recipe. [Training guide](https://github.com/bespokelabsai/nimble/blob/4edb0703a2e75d0170c3a45645a1961f4d1a2867/docs/NIMBLE_TRAINING.md)

Dependencies include Transformers 5.17.0, PEFT 0.21.0, Accelerate 1.15.0, SentencePiece 0.2.2 and Pillow 12.3.0; training instructions retain a CUDA PyTorch 2.8.0 wheel. The separate Qwen requirements pin PyTorch 2.14.0. They are different environments, not interchangeable guarantees. The inspected tree has candidate-data export scripts, but no documented supported ONNX/GGUF export for the trained Nimble adapter. [Training requirements](https://github.com/bespokelabsai/nimble/blob/4edb0703a2e75d0170c3a45645a1961f4d1a2867/requirements/training.txt), [Qwen requirements](https://github.com/bespokelabsai/nimble/blob/4edb0703a2e75d0170c3a45645a1961f4d1a2867/requirements/qwen.txt)

**Redistribution caveat:** the inspected GitHub tree has no root LICENSE, and GitHub's repository license field is null. The plugin skill's nested LICENSE is not a blanket license for the whole repository. The separately published model card declares Apache-2.0 and requires the base checkpoint in addition to its adapter. Obtain explicit root-code licensing clarification before bundling upstream code in Kingdom. This is an unresolved redistribution question, not a claim that reading or ordinary experimentation is prohibited. [Git tree](https://api.github.com/repos/bespokelabsai/nimble/git/trees/4edb0703a2e75d0170c3a45645a1961f4d1a2867?recursive=1), [published model card](https://huggingface.co/bespokelabs/Bespoke-Nimble-9B)

## Practical Kingdom design

1. Capture a fresh inventory before **each** selection: model identity/revision, provider, proven capabilities, availability, memory, latency receipts, node liveness/age, permissions, battery/charging, worker category, and free container budget. Reject stale, offline, unauthorized, or incompatible candidates in deterministic code before invoking a model.
2. Model selector chooses from the remaining installed model candidates plus `abstain`. Placement selector consumes the already-produced task graph and ranks bounded placement candidates; it does not author tasks. Recompute on inventory change and immediately before dispatch. An observing Knight is ineligible for coding unless the owner's policy explicitly permits it.
3. Train two compact local classifiers/rankers using Kingdom-owned structured features and candidate-relative features. This provides an actually trainable DT1 baseline without importing Nimble's 9B dependencies. Describe it as **Kingdom's lightweight decision models using Nimble-inspired contrastive data design**, never as fine-tuned Bespoke-Nimble weights.
4. Pair examples that change one decisive fact (offline/online, insufficient/sufficient memory, battery/charging, absent/present skill). Split by source task family and hardware/model identity to resist memorization. Keep synthetic policy-generated labels separate from observed task receipts. Good policy imitation scores do not establish faster jobs or correct real-world placements.
5. First run in shadow mode: log both selectors' suggestions beside the existing scheduler, collect execution success, elapsed time, peak memory and failures. Promote only after independent held-out tests and actual outcome comparisons; allow calibrated abstention and deterministic fallback. Never let a score grant tools, remove review, spawn unlimited containers or spend money.
6. Temporary Knights need host-enforced CPU/RAM/concurrency limits, task leases, authenticated job membership and cleanup after verification. Multiple containers share the same physical RAM and CPU; parallelism cannot manufacture extra capacity.

Ship the small artifact, feature/schema version, training provenance, hashes, supported input contract, held-out metrics and fallback policy together. Make Discord publication a separate approved artifact upload after testing; no external upload was performed here. Keep neural Nimble fine-tuning as an optional later GPU experiment with explicit resource and licensing checks, not a claimed completed DT1 training run.
