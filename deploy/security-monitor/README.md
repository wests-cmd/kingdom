# Deployment templates: not installed or enabled

These are review templates, not an installer. No account, key, unit or policy is created by the source change. Do not apply this drop-in to an existing Knight without a controlled identity/state migration and rollback plan.

- Use distinct fixed Linux principals `kingdom-monitor` and `kingdom-worker`. Resolve the real non-root worker UID and replace `12345`; the supervisor refuses its own UID and root as the allowed worker. Do not guess a UID or grant an arbitrary peer.
- Create the dedicated socket-access group `kingdom-monitor-client` through normal administrator provisioning. Only the authorized worker and supervisor need membership. The runtime directory must be supervisor-owned, group-readable/traversable but not group-writable (0750); the socket is 0660. SO_PEERCRED enforces the exact UID in addition to filesystem access.
- Protect `/opt/kingdom-monitor` code, interpreter, dependencies and `/etc/kingdom-monitor/supervisor.json` from worker writes, including every ancestor. Config must be a single-link regular file owned by root or supervisor, with no group/other write. Environment pinning and the worker launcher require equivalent root protection; changing or unsetting the requirement must not be a worker capability.
- Provision an **existing** raw 32-byte Ed25519 private key through a trusted administrator-controlled channel. No key-generation command or key material is supplied here. `signing.key` must be a single-link regular file, supervisor-owned, mode 0600 or more restrictive, with no symlink traversal. Pin its independently verified public key in `worker.env` (root-owned, no worker write). The supervisor never returns or logs the private key.
- The audit directory must be supervisor-owned 0700 and its regular audit file 0600. Events are append/fsynced before signing; the directory entry is fsynced at open. At 64 MiB the log refuses further signatures. Stop the service, archive/verify the existing evidence using a trusted operator procedure, and restart with an explicitly reviewed new audit file. The supervisor never deletes, truncates or silently rotates evidence.
- The service's watchdog bounds a stalled supervisor; a stalled/failed fsync yields no receipt, and clients deny high-risk authorization. This does not turn storage latency into a successful authorization. A restart conflict in standalone mode never unlinks an existing socket automatically; review it. Systemd owns and cleans only its dedicated RuntimeDirectory.
- A valid receipt proves the supervisor recorded an operation digest. It does not approve a task, grant tools, assess semantic safety, continuously monitor a running process, or replace a restricted effect broker. Existing same-account workers remain outside the OS-independence acceptance claim.

Before activation, verify actual account IDs, protected paths, filesystem fsync behavior, notification policy, worker identity/state preservation, inability to rewrite code/config/key, denied wrong-UID connections, supervisor-down high-risk denial, key rotation, and effect-broker mediation. The source tests do not establish that these conditions hold on the owner's live Knights.
